# Trying the preview

This guide takes about two minutes once the app is open. You need a local Git repository with at least one commit and a signed-in client for one provider.

## Verify the download

Download the macOS arm64 ZIP and `SHA256SUMS` from the same published [release](https://github.com/rjk6831/crewkite/releases). Read its release receipt for the exact source revision, tested macOS version, signing status and provider qualification.

From the folder holding both downloaded files, run:

```sh
shasum -a 256 -c SHA256SUMS
```

Extract the archive after the checksum passes. Keep its folder together. If macOS blocks opening it, retain the exact message with the candidate identity in your report. The [distribution notes](distribution.md) distinguish directory-package testing from signing and installation checks.

## Open the candidate

The preview has an ad-hoc resource seal. It has no verified Developer ID identity and is not notarized by Apple. Check the release receipt for the exact candidate's first-launch evidence.

Keep the extracted candidate folder together and double-click `CrewKite.command`. It opens the workspace through the adjacent `bin/desktop` launcher. The folder can move before its first launch. After setup, reopen the same folder to retain its projects, tasks and settings. To replace an initialized candidate, use the fresh package's `Upgrade Existing.command` and follow the [state-preserving upgrade procedure](distribution.md#upgrade-an-existing-directory-package). Keep the old app closed. The helper preserves the exact installed path and retains the original folder as a backup; moving its initialized state into another candidate folder is unsupported.

macOS can require separate approval for `CrewKite.command` and `Electron.app`. After each blocked attempt, use System Settings > Privacy & Security > Open Anyway for that exact item. Opening `Electron.app` directly can show its runtime welcome screen. Quit it with Command-Q, then launch `CrewKite.command` again.

The ad-hoc seal does not establish publisher identity, notarization or automatic Gatekeeper acceptance. Download quarantine can remain on an embedded executable after app approval. If the verified candidate still fails to open, retain the exact message and follow its release-specific first-launch instructions. Any folder trust step must name only that checksum-verified candidate and preserve its original quarantine metadata. A damaged-app message alone does not establish whether the bytes changed.

From Terminal, change into that candidate folder and use:

```sh
./bin/desktop
./bin/crewkite task list --json
```

I record the exact source revision, verification and provider qualification in the candidate's release receipt. A working launcher does not establish a qualified provider route. The [distribution notes](distribution.md) describe the directory package and remaining install checks.

## Walkthrough

1. Connect a provider. Open Settings in the left rail. Each provider has a card with its sign-in or connection state, the models it offers and the allowance it has left. Connect one provider there. For Local, press Connect in the card or in the left rail. It connects in place with the saved host, port and sign-in mode, and asks for a token only when the runtime needs one that CrewKite does not hold. A runtime with auth off on 127.0.0.1 connects with no token. Before a connection the card shows its last reading, marked "Last seen 2 h ago. Not connected.", with the controls off. [Provider routes](providers.md) lists what each provider needs first. Until one is connected, New thread shows a card that names the four providers and opens each one's Settings card, and Send stays off.
2. Add a project. Choose Add project in the left rail and select the root of a Git repository.
3. Start a thread. Choose New thread. The composer reads "Ask about this project or describe a change". Pick a provider and model from the menu in the composer, then ask about the project, for example "What does this project do and what would you change first?"
4. Watch it stream. The answer appears as the provider writes it. Each file read or search shows as a tool card, and a Thinking card appears for providers that report their reasoning. Two or more finished reads and searches in a row fold into one line, such as "Read 14 files", that opens into the cards. Choose Stop to end a turn early. When a Local reply stops at the output limit, the thread says how many reasoning and reply tokens it used and offers Continue, which asks the model to carry on from where it stopped. A message you send while a turn runs waits under the thread and starts when the turn ends.
5. Ask for a change. A permission request appears in the thread with the exact edit or command. Choose Allow once, Allow for this thread or Deny. The default is to ask every time. The edit lands in a scratch copy of the project, and your checkout is not touched.
6. Open Changes. Choose Open in Changes on the edit's tool card, or toggle the inspector and select Changes. It lists each changed file against the base commit, with the diff one click away.
7. Switch provider mid-thread. Open the provider and model menu, pick a model from another provider and send your next message. The reply runs on the new provider in the same scratch copy, and the turn is labelled with its provider. Each provider keeps one colour and a one-letter mark wherever it is named: O for OpenAI, A for Anthropic, G for Google and L for Local. The new provider starts from your messages, the earlier answers, the list of changed files and the patches that still fit. When you return to a provider after others answered, it resumes its own session and gets the turns it missed. If those do not fit, it starts a new session and the thread says so in one line. Changing the model inside a provider starts a new session too, and a handoff card names the reason, such as "model changed in the composer". Changing only the effort resumes the session. The menu also offers Continue on another provider, which moves the thread at once and adds a line such as "Continued on Anthropic from OpenAI." The inspector's Thread tab lists each turn under the message it answered. Its handoff setting moves the thread by itself when a provider reaches its limit, to the provider with the most allowance left or to the one whose allowance resets soonest, which spends that allowance before it resets unused.
8. Accept to a branch. In the Changes tab, keep the suggested branch name or type your own. The commit message field starts with the thread title and the first line of the last reply; edit it as you like. Choose Accept to branch. The controller commits the scratch copy's changes on a new local branch in your repository and shows the `git switch` line. The branch starts at the thread's base commit, the one Changes compared against, even if you have committed or switched branches since. The thread says so when HEAD has moved. Your checkout stays on its current branch, with nothing staged or modified. The thread's base then becomes the accepted commit, so Changes starts empty and a second Accept makes a branch on top of the first. ADR 0040 records why.
9. Push and open a pull request. Choose Push branch. The tab asks once whether to push the branch to origin with your own git credentials, and nothing is sent until you choose Push. The thread notes the push. Choose Open pull request next. With `gh` installed, the pull request opens on GitHub and its link shows in the tab. Without it, the tab copies the compare link for a github.com remote. Below that, the tab shows the branch's newest CI run and checks again every thirty seconds while it stays open. ADR 0037 records why each of these steps waits for your click.
10. Run a crew. Settings > General holds three presets: Solo, Pair and Full crew. Open the inspector's Crew tab, choose Start from preset and pick one, then set the flight mode. Manual runs nothing after a reply. Balanced runs up to three reviews, two fixes and a challenge, and asks before a command outside the read-only set, network access, work outside the scratch copy or a delete. Glide runs the same chain and stops only on a failure or a permission your policy does not cover, and it turns automatic handoff on. The pill beside the model picker shows the mode and opens the Crew tab. Under Thread, Handoff mode picks where the thread continues when a limit is reached: Most allowance left, Resets soonest, Even spend or Local first. Hover each name for its rule. While a reply runs, a queued message shows Send now beside Remove. Send now stops the current reply and starts that message with the work so far. ADR 0038 records the rules.
11. Attach files. Choose the paperclip at the left of the composer bar, drop files on the composer or paste a copied file or screenshot into the box. Each file shows as a chip above the box: a thumbnail for a picture the system can decode, and the name and size for anything else. The chips stay on your message in the thread from the moment you send it, and do not wait for the reply. A message holds up to 32 files. Attaching works before the first message of a thread and on a message that waits in the queue. Send waits until the files are copied, and it needs some text. CrewKite copies each file into its own folder under the CrewKite home, so Accept never carries it into your repository. Each provider receives the file in the form its client takes, as [Provider routes](providers.md#chat-adapters) describes. The chip tells you how the selected provider gets the file. A file sent as a path says so, such as "Sent as a file path. Anthropic can open it with its tools." A file the provider cannot take shows a warning, such as "Local cannot take this file. The turn will stop and offer another provider." Sending still works. Click an image or PDF chip to preview it, with Quick Look on a Mac. Press Enter on a focused chip to do the same. The chip menu has Reveal in Finder and Save as, and both work only on files in the CrewKite home. ADR 0039 records the rules.
12. Try with. When a provider's client refuses the files, the thread shows the failure with Try with beside Retry. Try with lists each connected provider that has not yet tried that message. Providers whose client reported that it takes every file type on the message come first, and the rest follow in the thread's handoff mode order. Choose one to run the message again there. The thread continues on that provider with a handoff line, and the files go with it.
13. Retry and Regenerate. A failed or stopped turn shows Retry under its failure line, and the newest reply shows Regenerate. Each has a model menu beside it, set to the thread's current model. A model on another provider moves the thread the way Continue on another provider does. Regenerate adds a "Regenerated" line and keeps the earlier reply above it. Only the newest turn can run again, and only while no reply is running.
14. Discard a file. Each file in Changes has Discard. It asks first and names the file. A changed file goes back to the base commit, a file the thread added is removed and a file the thread deleted comes back. Accept then carries only what is left. Discard waits while a reply runs. A link from the base that the thread replaced or removed shows in Changes with that reason. Accept takes the base link, and Discard puts it back in the copy. Discard does not apply to entries the scratch copy could not hold: submodules, links that lead outside the repository and paths that are not UTF-8. Changes lists those under "Skipped N entries the scratch copy cannot hold", and Accept takes them from the base commit unchanged.
15. Rename and delete a thread. Click a thread's title in the header to edit it. Enter saves and Escape cancels. The menu beside a thread in the left rail has Rename and Delete. Delete asks first. It removes the thread, its scratch copy and its attached files, and the branches you accepted from it stay in your repository. Delete waits while a reply runs.
16. Read the rail. The dot beside each thread shows Idle, Running, Waiting for permission or Last reply failed. When a reply finishes or fails, a crew finishes or stops, or a permission request waits, and the window is in the background or another thread is open, CrewKite posts one system notification titled with the thread and the event, such as "Fix rounding: reply finished". Each thread posts at most one notification every five seconds. The dock badge counts the threads with news you have not opened. Click the notification to open the thread. Opening a thread clears its news.

A turn that a crash leaves open shows as failed, with a plain reason, when the controller restarts. Reopening starts no work beyond the messages you queued, which start once the thread is free.

## Send a short record

Keep a short record of what you asked, which provider answered, any refusal or error line, what Changes showed, and whether the next action was clear. A few sentences is enough. The [roadmap](roadmap.md) lists the open evidence gates.
